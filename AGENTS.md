# Правила работы с проектом ScanMarket

## 1. Назначение проекта

ScanMarket собирает товары из избранного интернет-магазина и сохраняет в SQLite сведения о товарах и историю изменения цен.

Сейчас поддерживается Ozon. Архитектура и изменения должны по возможности сохранять основу для подключения других магазинов.

## 2. Язык и общие правила

- Общайся с пользователем и пиши документацию по-русски.
- Исполняемый код проекта и вспомогательные утилиты пиши только на Script — языке движка Qode.
- Не добавляй Python, PowerShell, JavaScript или другие языки для обходных решений.
- Если нужной возможности Script/Qode нет, не подменяй её другим языком. Подготовь конкретный промпт на разработку или исправление библиотеки/движка.
- Соблюдай синтаксис и стиль существующих `.prg`-файлов.
- Перед использованием возможностей языка сверяйся с документацией `docs/*`. Краткая справка — `/docs/specs/qode.md`.
- Библиотека базовых скриптов для автоматизации /scriptlib/*
- Документация может отставать от реализации. При противоречиях проверяй существующие рабочие примеры.
- Не преобразовывай Script в JavaScript, C++, Python или другой похожий язык.
- Не применяй синтаксические конструкции, которые выглядят привычными для других языков, но не подтверждены реализацией Qode.
- В итоговом ответе сообщай результат и важные ограничения кратко, без рассуждений.

## 3. Форматирование и стиль кода

**Это обязательные правила для всех новых и изменяемых `.prg`-файлов. Код должен быть аккуратным, единообразным и удобным для чтения.**

### 3.1. Общие требования

- Всегда форматируй код с нормальными отступами и переносами строк.
- Никогда не записывай весь скрипт в одну строку или в несколько чрезмерно длинных строк.
- Одна инструкция — одна строка, если её разумно можно разместить таким образом.
- Используй 4 пробела для каждого уровня вложенности.
- Не используй табуляцию для отступов.
- Ставь пробелы вокруг операторов: `=`, `==`, `!=`, `+`, `-`, `<`, `>`, `and`, `or`.
- После запятых ставь пробел.
- Не добавляй случайные пробелы внутри скобок и вызовов функций.
- Не допускай смешивания разных стилей форматирования в одном файле.

### 3.2. Функции и блоки

- Объявление каждой функции начинай с новой строки.
- Открывающую и закрывающую фигурные скобки размещай на отдельных строках.
- Содержимое блока обязательно выделяй отступом.
- Условия, циклы и вложенные блоки оформляй аналогичным образом.
- Не объединяй несколько инструкций в одну строку через `;`.
- Даже короткие условия оформляй многострочно, если это улучшает читаемость.

Пример:

```
function showProduct(rowIndex)
{
    if (rowIndex == null or rowIndex < 0)
        return;

    var q = db.query();

    q.open("select * from products");

    if (q.eof())
    {
        q.close();
        return;
    }

    q.close();
}
```

### 3.3. Переменные и выражения

- Каждую переменную объявляй на отдельной строке.
- Не объединяй несколько объявлений `var` через `;`.
- Сложные выражения разбивай на логические части.
- Тернарные операторы оформляй многострочно, если выражение длинное.
- Не сокращай понятные имена переменных ради уменьшения размера кода.
- Сохраняй существующие имена функций, переменных и параметров, если переименование не требуется задачей.

Пример:

```
var id = str.toString(q.field(0));
var name = str.toString(q.field(1));
var brand = str.toString(q.field(2));

var currentPrice = null;
var lastUpdate = "Нет истории";
```

### 3.4. SQL-запросы

- Длинные SQL-запросы обязательно разбивай на логические строки.
- Строки с подстановками строй через интерполяцию `\(выражение)` — она читается легче, чем конкатенация с `+`. Конкатенацию применяй, когда нужно перенести длинную строку на несколько строк или интерполяция затрудняет читаемость.
- Отдельно выделяй основные части запроса: `select`, `from`, `where`, `order by`, `limit`.
- Не записывай длинные SQL-запросы одной строкой.
- Не меняй логику SQL-запроса при форматировании.
- Не удаляй условия фильтрации, сортировки и ограничения выборки.

Пример:

```
var q = db.query();

q.open(
    "select product_id, name, price " +
    "from products " +
    "where source = 'ozon' " +
    "order by name collate nocase"
);

q.close();
```

### 3.5. Пустые строки и комментарии

- Используй пустые строки для разделения логических блоков.
- Не ставь пустую строку после каждой инструкции.
- Отделяй комментариями крупные функциональные разделы.
- Комментарии должны объяснять назначение или причину реализации, а не пересказывать очевидный код.
- Не добавляй комментарий к каждой переменной и каждой строке.
- Для крупных файлов допускается использование разделителей:

```
// ============================================================
// Работа с базой данных
// ============================================================
```

- Не создавай чрезмерное количество комментариев и визуального шума.

### 3.6. Длинные строки

- Старайся, чтобы обычные строки кода не превышали примерно 100–120 символов.
- Если выражение длинное, переноси его на несколько строк.
- Длинные вызовы функций, условия и конкатенации оформляй с логическими переносами.
- Не жертвуй читаемостью ради минимального количества строк.

### 3.7. Сохранение синтаксиса Script/Qode

При форматировании обязательно сохраняй оригинальные конструкции языка.

В частности, не заменяй:

- `or` и `and` на `||` и `&&`;
- `#[...]` на обычные массивы JavaScript;
- особенности работы с `null`;
- специфические методы `str`, `file`, `db`, `qt`;
- особенности объявления и использования функций;
- особенности работы с объектами и формами Qode.

Не изменяй синтаксис только потому, что он отличается от привычного JavaScript.

Форматирование не должно превращаться в рефакторинг или изменение поведения программы.

### 3.8. Форматирование Script внутри JSON

Если Script хранится внутри JSON в виде строкового значения:

- Сохраняй корректную структуру JSON.
- Правильно экранируй кавычки и специальные символы.
- Не удаляй необходимые `\n` и другие escape-последовательности.
- Не превращай многострочный Script в одну длинную строку без необходимости.
- Сохраняй читаемость самого Script, а не только внешнего JSON.
- После изменения проверяй корректность JSON и содержимого скрипта.

## 4. Среда запуска

- `qode.exe` — чистый консольный движок, в том числе для утилит, которым не нужен Qt.
- `qodeqt.exe` — консольный движок с Qt-адаптером; сканирование использует его SQLite-модуль `db`.
- `qodegui.exe` запускает GUI-конфигурацию.
- `qodedesigner.exe` редактирует JSON для GUI.
- Это не текущая цель этапа сбора цен. Не начинай GUI-визуализацию без отдельного запроса.
- Текущий этап: сбор Ozon через `qodeqt.exe`, пригодный для запуска планировщиком Windows.

## 5. Правила изменения проекта

- Сначала изучи относящиеся к задаче `.prg`-файлы, модули и `config.json`.
- Не полагайся на старые заметки о дефектах движка.
- Не меняй движок или файлы вне проекта.
- Если обнаружен дефект движка, отдели его от ошибки приложения и подготовь минимальный тест и промпт для исправления.
- Не удаляй и не перезаписывай пользовательские данные, профиль браузера, cookies, базу или диагностические файлы без прямого разрешения.
- Сохраняй совместимость с путями Windows, включая каталоги с пробелами.
- Настройки бери из `config.json`. Не дублируй конфигурацию без необходимости.
- В SQLite создавай новую точку в `price_points` только при изменении текущей цены.
- Не записывай секреты и содержимое cookies в логи или документацию.
- При изменении парсера Ozon сохраняй фильтрацию рекомендаций и рекламы.
- Сохраняй проверку реального рендеринга избранных карточек: DOM магазина может меняться.

### 5.1. Код возврата программ (важно)

- Каждая точка входа (выполняемый `.prg` из корня, `tools/`, планировщика) обязана явно завершать успешный путь
  выражением `return 0;` (или `system.exit(0)`), а путь ошибки — `system.exit(<ненулевой код>)` / `return 1;`.
- Не полагайся на неявный результат движка: если в конце скрипта нет `return`, qodeqt возвращает `AsInt()`
  последнего выражения — значение непредсказуемо (например, `check_product_state` без `return` давал код 52).
- Пока ядро не исправлено (чтобы возвращать 0 по умолчанию), при добавлении новой утилиты сразу добавляй явный
  `return 0;` в конец и `system.exit(1)` на путь ошибки.
- Проверка запуска инструмента должна опираться на `$LASTEXITCODE` (0 = успех), а не на то, что скрипт просто дошёл
  до конца.

## 6. Проверка изменений

- Для сканирования и браузерных сценариев используй `qodeqt.exe`.
- Для `tools/scanutils.prg` можно использовать `qode.exe` если не требуется доступ к базам данных, но универсальный `qodeqt.exe` лучше он всё поддерживает.
- Предпочитай проверки без записи в базу и без изменения авторизованного профиля.
- Если проверка изменяет данные, предупреди об этом.
- После правок документации сверяй команды и имена параметров с текущими скриптами и `config.json`.
- Не объявляй тест успешным, если он не запускался.

## 7. Самопроверка перед завершением задачи

Перед передачей результата обязательно:

1. Проверь, что весь изменённый Script отформатирован и имеет единый стиль.
2. Проверь отступы, переносы строк, расположение фигурных скобок.
3. Убедись, что отсутствуют длинные однострочные конструкции, которые можно было разбить.
4. Проверь, что синтаксис соответствует Script/Qode, а не JavaScript.
5. Убедись, что форматирование не изменило логику программы.
6. Проверь корректность SQL-запросов и строковых выражений, если они изменялись.
7. Если изменялся JSON, проверь его синтаксическую корректность.
8. По возможности выполни проверку скрипта соответствующим движком.

**Главное правило:** приоритет — корректность Script/Qode, сохранение поведения программы и читаемость кода. Компактность и минимальное количество строк не являются целью.
