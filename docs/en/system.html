Process execution

FunctionDescription
system.system(cmd)Synchronous command execution
system.exec(cmd, [timeoutMs])Run a command and capture stdout/stderr. Returns {success, code, stdout, stderr}; default timeout is 60 seconds
system.systemex(cmd, [workDir], [timeout])Hidden launch with a working directory and timeout. Returns {success, code, killed}
system.systemasync(cmd, [workDir], [timeout], [options])Asynchronous. Returns a Process object. options controls console attachment (see below)
system.execArgvAsync(argv, [opts])Asynchronous shell-less launch by an argument array. Returns a Process object; on completion result is #{"success","code","killed","stdout","stderr"}. opts: {"cwd","timeout","outfile","errfile","console"}

The optional options argument is a tuple #{"console": "..."} that controls the child process attachment to the parent console:

  • "inherit" (default) — a console child process may share the parent console;
  • "new" — CREATE_NEW_CONSOLE: a separate console for a console child (ignored by Windows for GUI apps);
  • "detached" — DETACHED_PROCESS: the child process does not use the parent console. Recommended for browsers/long-running GUI apps.

Example: system.systemasync("start chrome ...", "", 60000, #{"console": "detached"}). An unknown console value returns a diagnostic error. Existing calls without options behave as before. A child process without DETACHED_PROCESS/CREATE_NEW_CONSOLE may share the parent console and change its modes — see the Log module for diagnostics/restore (Log.consoleInfo()/Log.refreshConsole()).

On Windows, system.exec currently runs the command through cmd.exe /c. On timeout, the process is terminated and success is false; do not treat code as the command's exit code after forced termination.

system.execArgvAsync(argv, opts) — asynchronous shell-less launch by an argument array: argv[0] is the executable, the rest are arguments (no escaping needed). opts — #{"cwd","timeout"(ms),"console": "inherit"|"new"|"detached","outfile","errfile"} — same as system.execArgv. Returns a Process object (isReady, kill()); on completion Process.result is #{"success","code","killed","stdout","stderr"}. stdout/stderr are collected from outfile/errfile, or, when those are not set, from temporary files that are created and removed automatically. A failed launch cannot throw in the background worker: success=false and the message is placed in stderr.

var proc = system.execArgvAsync(#[exe, "arg1", "arg2"], #{"timeout": 30000});
while (!proc.isReady) system.sleep(0.05);
var r = proc.result;
print("code=" + r.code + " out=" + r.stdout + " err=" + r.stderr);

system.getcommandline()

Returns a tuple:

KeyDescription
app / basename / dirname / filenameInformation about the executable (qodeqt.exe)
argv0The first argument as passed by the shell (normalized)
rawAll arguments as-is, in order (raw[0] is the script path for qodeqt)
argsOnly non-flag arguments (the script path is the first element)
countNumber of non-flag arguments
flagsParsed flags: --name=value, --flag, grouped short flags -abc. A value from = is converted to bool when recognized (true/false/1/0/yes/no/on/off). A repeated flag keeps the first value (tuple/emplace semantics — see the cli library for an explicit policy)
parsedOrdered tokens for CLI libraries: each element is #{"flag": name}, #{"flag": name, "value": string}, #{"pos": text} or #{"end": 1} (the -- separator, after which everything is positional). Values from = are stored as raw strings (type coercion is up to the consumer). parsed[0] is the script path

In flags/args, -- behaves as before (the separator is not put into args; subsequent -… tokens still go into flags); correct end-of-flags handling is done through parsed. A full argparse-style flag schema is provided by the cli library.
